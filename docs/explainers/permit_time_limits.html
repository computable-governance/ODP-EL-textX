Permit time limits and responses

A permit can carry a time limit in its deadline: a duration such as "5 minutes", a date or instant such as "by 2026-05-20", or the unquoted name of a Policy of type duration, whose declared value is the limit (policy ShortNotice : duration { initial_value: 5 minutes }, then deadline: ShortNotice). The engine enforces that limit. When an actor tries to use a permit whose time is up, the engine refuses the action. A permit whose time is up only moves to its new state, expired, when the sweep runs; a violation response can also suspend or expire a permit (section 4).

permit timedPermit {
    for_action: "useTimed"
    state: active
    deadline: "5 minutes"
}

timedPermit is only the name of this declaration. The deadline line is what makes the permit timed; without it this is an ordinary permit. Here "5 minutes" means 5 steps (see below).

Before you start: time in the engine

The tick. The engine keeps one counter, the tick. It starts at 0 when a specification loads. Each act that goes through moves it up by 1: an action run with advance(), a revoke, a reinstate, a discharge, an event or a declared violation. A refused act leaves it unchanged, and so does a revoke that finds every instance of the permit expired. The sweep adds 1 only if it changed something. Firing violation responses adds 1 if any response fired, even if its clauses changed nothing. advance_clock(ticks) is the one call that moves it by more than 1: it lets time pass with no action, and it is refused while a strict burden is active and its holder is enrolled.

advance(). This is how an actor does something. The engine checks, in order, the actor (enrolled, and filling a role that declares the action), the strict-burden guard, the preconditions, any embargo and the permits the action needs. If every check passes, it applies the action's effects and moves the tick by 1. The use check below is the permit step inside advance().

A step is one minute, but not on a wall clock. A deadline such as "5 minutes" means 5 steps. The engine turns each unit into minutes and rounds up, so "5 days" is 7200 steps. A permit with "5 minutes" runs out five ticks after its start tick: five acts, or one advance_clock(5), however much real time passes.

Two clocks. The step clock is the tick; it judges duration limits. DeadlineClock is separate; it judges only date and instant limits, against the as_at date the caller passes. With no DeadlineClock, a date limit is never judged.

One caution. The tick is both a count of elapsed time and a count of events (the toolchain records this as an open finding). Read "5 steps" as "5 moves of the engine", not as a promise about real time.

Compelled and detectable. The tick is also how the toolchain separates two ends of an obligation. For a strict burden, the holder cannot simply wait: while it is active, advance_clock() is refused, so is any act that discharges nothing, and the verifier's tick transition is suppressed. The only way forward for the holder is to discharge it: discharge is compelled. For an ordinary (eventual) burden, time can pass without the act; the tick keeps counting until the deadline in steps is reached, and then the sweep can flag the burden as violated. That obligation is only detectable: the engine can tell afterwards that it was missed, but it could not make it happen.

Why this matters for permits. A permit's steps are always counted on the tick, both at use and in the sweep. A strict burden stops advance_clock() and every action that discharges nothing, but the tick still moves when something else goes through: another burden is discharged, a violation is declared, a violation response fires, or the sweep violates an ordinary burden or expires a permit. The step count a watchdog passes to declare_violation() (at_tick) judges only the burden's deadline, never a permit's time. So a strict burden whose discharge needs a timed permit can get stuck: once the permit's time is up, before the burden became active or while the tick moved on as above, the discharge is refused, and the sweep never violates a strict burden. Only a declared violation ends it. The verifier has no permit time and would still show the discharge as reachable, which is why compelled is withheld for such a burden.

A violation response that suspends or expires the permit is a second way into the same stuck state. The status route withholds compelled for that case too, with its own status (section 4).

The use check

The test the engine runs when an actor tries an action that needs a permit (advance() Step 6, which declare_violation() shares). It refuses the action if the permit's time has run out, and leaves the permit's state and the tick as they are. It checks a duration limit only. A date or instant limit is not checked at use.

The sweep

The engine's pass over live state, run when a caller asks for it (check_live_violations(), or POST /check-violations). It is the only place that writes expired for a time limit; a violation response's expires: also writes it (section 4). It judges both forms: a duration limit by the same test as the use check, and a date or instant limit against the caller's as_at, but only when the runtime has a DeadlineClock. Without one it writes a not judged line and leaves the permit as it is. The sweep reads active and pending permits only.

The start tick. A duration limit counts steps from the permit instance's start tick, which is the tick of its first activation (its grant tick if it is granted active). A permit that has never been active has no start tick, so a duration limit never elapses for it. A restore (effect activate, the triggering event, a reinstate) never changes the start tick. Steps keep counting while the permit is pending (this includes a permit a response suspends) or superseded. Only a new grant gives a new start tick. A clone or a transfer copies the old one. A limit with no measurable magnitude, for example "thirty days", never elapses.

1. The permit states

expired is final for that instance. It is not lapsed: expired means the time limit is up (ledger cause deadline) or a violation response expired the permit (cause response), while lapsed is a claimable token whose sibling in an any_discharged group was claimed (cause sibling). The two are unrelated.

  • Entering a state
  • 1start → active: grant (declared active), effect create, first reinstate
  • 2start → pending: grant (declared pending)
  • 3start → claimable: grant (declared claimable)
  • Between active and pending
  • 4active → pending: effect pend, or a response's suspends: (section 4)
  • 5pending → active: effect activate, triggering event, or reinstate
  • Reinstate
  • 6claimable → active: reinstate
  • 7lapsed → active: reinstate
  • 8superseded → active: reinstate
  • Revoke
  • 9active → superseded: revoke
  • 10pending → superseded: revoke
  • 11claimable → superseded: revoke
  • 12lapsed → superseded: revoke
  • Siblings in an any_discharged group
  • 13active → superseded: sibling discharged
  • 14claimable → lapsed: sibling claimed
  • Time limit, or a response's expires:
  • 15active → expired: sweep, time limit up, or a response's expires:
  • 16pending → expired: sweep, time limit up, or a response's expires:

A revoke here is either a direct revoke or a ViolationResponse's revokes:. A response revokes only when some instance of the permit is active. No act moves a permit into claimable: a permit is in that state only if the author declares it so, and claim() claims burdens only. A clone or a transfer copies an instance in its current state, whatever that state is. A response's suspends: and expires: act only on the Authorization's own holder, or on each actor filling its to_role; on any state other than the ones shown they change nothing and write note lines.

2. Four timelines

In all four timelines, the permit P has deadline: "5 minutes" (5 steps) and is granted active to H at tick 3, so its start tick is 3.

(a) A use refused past the limit

(b) The sweep expires the permit

(c) A reinstate blocked on an expired permit

(d) A new grant gets a new start tick

A ViolationResponse's creates_burden may name a permit. It grants a new instance unless the recipient already holds the token active, and an expired instance does not count.

violation_response GrantOnBreach {
    on_violation_of: breachedBurden
    obligates: H
    response_kind: remediate
    creates_burden: P
}

4. Violation responses that suspend or expire a permit

A violation response can name an Authorization in suspends: or expires:. When the response fires, the permit that Authorization grants moves to pending or to expired. Each clause names one Authorization per line and may be repeated. When a response has several of these clauses they come in the order revokes, suspends, expires.

violation_response SuspendOnBreach {
    on_violation_of: breachedBurden
    obligates: Issuer
    response_kind: remediate
    suspends: TimedAuth
}

In the diagram and timeline below, TimedAuth is the Authorization that grants the permit P to H, and Issuer is its authority.

suspends:

moves the permit from active to pending. "Active" is judged by the permit's state, not by the use check, so an elapsed permit that the sweep has not yet written as expired can still be suspended. Its steps keep counting while it is pending.

expires:

moves the permit from active or pending to expired. expired keeps its meaning: it is final for that instance. A response's expires: is a second way to reach it, beside the sweep; there is still no way out except a new grant.

Whose instance. The target is the Authorization's to_agent instance, or the instances held by the actors who fill its to_role. Another holder's instance is never touched. Identical duplicate instances both move. A response's revokes:, by contrast, acts on a permit by name, for every holder.

  • 1active → pending: a response's suspends:
  • 2active → expired: a response's expires:
  • 3pending → expired: a response's expires:

Order and tick. In one firing, the terminate chain or revokes: comes first (they exclude each other), then every suspends: line, then every expires: line, each in written order. Naming the same Authorization twice gives no-effect note lines the second time. The tick moves on by one per call when any response fired, even if nothing changed. There is no strict-mode guard, no embargo is touched, and the Authorization need not be revocable.

Authority. The Authorization's authority must be the response's obligates. The validator checks it with the error [response-permit-authority], one per line, and the engine checks it again when the response fires. That only the Authorization's authority may suspend or expire its permit is this toolchain's reading; the clause is to be confirmed.

Ledger and note lines. An instance moved by suspends: or by a response's expires: writes the cause response, with the response's name as ref. A response's revoke still writes revocation, with the Authorization's name, and the sweep's expiry writes deadline. Token events show the net change over one call, so suspends: then expires: on one permit gives a single event, active to expired. The note lines, shown for suspends::

not suspended 'A': authority is '<authority>', not '<obligates>'
not suspended 'A': no actor fills role '<role>'
not suspended 'A' (to 'X'): no instance of permit 'P'
suspended 'A' (to 'X')
  pended permit 'P' held by 'X'
not suspended 'A' (to 'X'): nothing to suspend
  suspend 'P' had no effect: 'X' holds it <state>

For expires: the words are expired, expire and expired permit; an authority mismatch, a role no actor fills, or no instance of the permit writes one line and changes nothing; otherwise a headline is followed by one indented line per instance, so a complete no-op writes two lines.

The status route

The verifier reads neither clause. For a strict burden whose discharging action needs a permit granted by an Authorization that any response in the specification names in suspends: or expires:, GET /obligations/{token_name}/status answers compelled: null and status: "permit suspension or expiry by a response: not modelled", in both modes. The test reads only the specification, so the answer is the same before and after a firing. For a permit with a time limit the status is "permit time limit: not modelled", and that one takes precedence. Only compelled is withheld. A permit named only by a response's revokes: is not covered: the static answer there stays compelled: true.

What this does not close

  • The recommended action (its route, and the one execute-action returns) and GET /kripke/witness still offer the refused path. Only the status route withholds.
  • compelled stays as computed for a strict burden that a declaration can violate (parity row R8), or whose discharging action has a precondition (R11).
  • detectable can be falsely true, because the model's discharge path can need a use the engine refuses (R28).
  • A date limit with no DeadlineClock is never judged, so it never takes effect. The status route still withholds compelled for it.
  • The withholding finds the burden among top-level tokens only. For a burden declared inline in a role, the status route answers 404.
  • A pending or expired permit at the hybrid model's anchor (R29). In the hybrid model an action that emits the permit's triggering event can restore a pending permit, but not on every path: an action that discharges a burden with no discharged_by, for example, is not modelled as firing its event, so it restores nothing. An event that no action emits never restores it. A reinstate or an activate effect does not restore a pending permit in the model, and no edge changes an expired permit at the anchor.
  • A permit withdrawn by a response's revokes: is not covered by either status. In mode=spec the route still says compelled: true for a strict burden that needs it.

Limits

  • No route re-grants a permit. A new instance comes only from a response's creates_burden, or from a direct grant_token() call, which leaves no ledger event.
  • A clone or a transfer keeps the old start tick and state, so it never renews a permit.
  • A strict burden whose discharge needs a timed permit can get stuck. Once the permit's time is up the discharge is refused, and the sweep never violates a strict burden ([W-strict-timed-permit] warns).
  • A limit with no measurable magnitude never elapses, and the status route does not withhold compelled for it. [W-strict-timed-permit] still fires on it.
  • A violation response's suspends: or expires: on the permit a strict burden's discharge needs can leave the burden stuck in the same way, if the response fires while the burden is active. The status route withholds compelled for it.
  • A reinstate of an Authorization with no on_revocation embargo raises an error, so a permit suspended under such an Authorization comes back only by effect activate or by its triggering event.
  • A restore acts by permit name across holders, so with several holders a suspended instance can stay pending after a reinstate.
  • On an expired permit a response's suspends: and expires: change nothing and write note lines, and the response still fires and moves the tick.
