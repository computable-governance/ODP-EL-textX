## Main outcome: T5 (Exercise) — Permit/Embargo given real Kripke semantics

Investigating the IT-governance question led to checking why Permit/Embargo
deontic tokens were never consulted by the existing T1/T2/T3 Kripke
transitions. This turned into the day's substantive work.

**Theoretical grounding (chat discussion, not yet written up for a paper):**
Classical Standard Deontic Logic (Kripke 1963/Chellas 1980, system KD —
same lineage the paper's AF/EF/AG already sits in) defines permission as
the dual of obligation: P(p) =df ¬O(¬p). Mapped onto the toolchain's
existing CTL vocabulary: Burden↔AF, Permit↔EF, Embargo↔AG(¬p). ISO 15414
Annex C itself is silent on Permit/Embargo — its "four ideas" (per
EDOC26final.tex §3.4) cover only the obligation/Burden case — so this
extension is genuinely novel relative to the paper's "first complete
implementation of Annex C" claim, not filling an acknowledged gap in it.
Candidate future paper angle, not yet scoped.

**Implementation (toolchain/el_kripke.py, four reviewed diffs + tests):**
- `World.occurred_actions` — new frozen field, action-indexed (not
  token-indexed, since a Permit is a standing grant and must not transition
  on exercise). `_make_world` signature change propagated across all 14
  existing call sites (`build_kripke_model`, `build_kripke_from_runtime`,
  `_run_consent_scenario`).
- `PermitDescriptor` / `_build_permit_descriptors()` — Tier-1 only
  (explicit `for_action`); Tier-2 structural fallback (`requires_permit`/
  `ConditionalAction`, mirroring `_find_action_for_burden`) deliberately
  deferred — confirmed by repo-wide grep that no current scenario needs it.
- **T5 (Exercise)** — new transition rule generating action-occurrence
  edges for `ACTIVE` Permits with a resolvable holder. Self-loop guard
  added (undocumented in the original spec, correctly identified as
  necessary by CC) to prevent redundant re-firing once an action has
  occurred.
- **Embargo guard on T5** — corrects an assumption in the original design
  spec: `DeonticToken.inhibited_by_embargo` (STRING field) is dead code,
  confirmed unused repo-wide. Real linkage is Action-scoped
  (`action.deontic_requirements` / `ConditionalAction.inhibited_by`).
  Guard is actor-scoped, verified against `el_reasoner.can_perform()`
  (el_reasoner.py:367-371, 404-406) verbatim before implementing — an
  Embargo only blocks if held by the *same* actor performing the action.
- `_build_propositions` — added `"occurred:<action>"` propositions;
  without this, T5 wrote facts invisible to the model's actual
  `satisfies()`/`AF`/`EF`/`AG` query surface.
- Tests: `tests/test_t5_exercise_embargo_guard.py`, 3 functions — exercise
  fires; suppressed when Embargo held by same actor; not suppressed when

## Findings logged to CONCEPTS_INDEX.md today
1. Governance-engine builder accountability gap — verifier-logic vs.
   bypass-path failure modes, distinct from the AIVendor gap.
2. Permit/Embargo missing domain scope (§7.8.8.2/§7.8.8.3) — Permission
   and Prohibition are each defined in the standard as starting with "an
   authorization domain," but `domain_scope` exists only on `Authorization`
   today, not on bare `DeonticToken`. T5's Embargo guard is explicitly
   single-domain-scoped as a result; federation-crossing behaviour is
   undefined pending this fix (§7.8.8.4 confirms federation-crossing effect
   is contract-determined, not automatic).
